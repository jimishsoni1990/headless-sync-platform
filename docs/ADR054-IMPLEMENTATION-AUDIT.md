## 0. Context & audit method

The Blog-MVP pipeline (P0/P1A/OPS/OPSC/ONB) shipped **before** ADR-054. It bakes in the **v1.0 daemon execution model**: long-running `WorkerEngine::run()` loops, one supervised process per strategy, `usleep` idle back-off, graceful `shutdown()`, and worker identity "self-assigned at startup … never changes during the worker lifetime." ADR-054 makes **WP-Cron the ONLY v1.x execution mechanism**: bounded, stateless, time-budgeted **cycles** invoked per cron tick; overlap-safe via **existing guarantees only** (SKIP LOCKED + aggregate versioning + visibility timeout + DECISION 3 commit — **no new locking mechanism**); heartbeat reinterpreted as per-cycle **cycle-freshness**; metrics drop `worker_uptime`/`restart_count`; class names (`WorkerEngine`, `*WorkerStrategy`, `WorkerExecutionContext`) **retained** — audit semantics, never rename.

**Preserved unchanged by ADR-054 §9 (must NOT be touched by any alignment work):** the Outbox→Relay→Dispatcher→Queue→Processing pipeline; the per-event pipeline (Claim→Load→Context→Validate→Resolve→Execute→Commit→Ack); DECISION 3 three-op single-PG-transaction commit; DECISION J stale guard; SKIP LOCKED claiming; visibility timeout (DECISION R); replay (DECISION T); reconciliation (DECISION U); four-connection topology (DECISION L Ruling 0); heartbeat schema (DECISION P — `system.worker_heartbeats`); derived-metrics discipline (DECISION Q); correlation/causation IDs (ADR-037); at-least-once + idempotent redelivery.

**Central finding (whole-tree):** the pipeline currently has **no execution trigger at all** except the reconciliation cron. Nothing in production calls `WorkerEngine::run()` — there is no CLI worker command, no activation scheduling, and no WP-Cron registration for relay/dispatch/projection/maintenance. The daemon `run()` loops exist but are un-launched. ADR-054 requires a **new** WP-Cron-triggered Processing Engine entry point that composes the four consumer-side stages into one bounded cycle. This is therefore predominantly an **additive** alignment (build the cycle entry point) plus a **behavioural correction** of the daemon-loop surfaces, not a rewrite of the per-event pipeline.

**Two NEW FLAGS were surfaced (needed-ruling, not resolved here):** FLAG-ALIGN-1 (per-cycle worker-identity UUID semantics + heartbeat `status` value set) and FLAG-ALIGN-2 (DECISION W (c) backfill worker-heartbeat prerequisite under cycle-freshness heartbeats). See §6.

## Deliverable 2 — Implementation Alignment Plan

Task list grouped by subsystem. Each task cites its authority. **Constraints (ADR-054 §9, binding on every task):** no new locking mechanism, no fifth PG handle, no new `pg_*` wrapper, no schema change may appear in any task.

### A. Processing Engine (the core new work)

- **T1 — Build the WP-Cron Processing Engine cycle.** A bounded, stateless, single-PHP-execution entry point that runs, in order: relay batch → dispatch batch → projection batch → maintenance (as scheduled) → persist operational metrics → clean exit. Reuse the **existing** stage primitives verbatim: `RelayWorkerStrategy::tick()` (relay), `DispatcherWorkerStrategy::execute()` (dispatch), `EventWorkerStrategy::execute()` in a bounded loop (projection), `MaintenanceWorkerStrategy` (maintenance). Enforce per-stage max batch sizes + an execution-time budget checked before each stage and before each projection claim; on budget, stop claiming, finish the in-flight event's single transaction (DECISION 3), persist metrics, exit. **Retain the class name `WorkerEngine`** (or add a cycle method to it) — no rename (ADR-054 §8). *Authority: Doc 8 v2.0 §9/§12; ADR-054 §1.*
- **T1a — Retire the daemon loops from the execution path.** `WorkerEngine::run()`/`shutdown()`, `RelayWorkerStrategy::run()`/`shutdown()`, and `DispatcherServiceProvider::dispatcher.engine` are daemon surfaces with no v1.x trigger. Remove them from the execution path (the cycle replaces them). The per-stage `tick()`/`execute()` primitives and all strategies are **kept**. **BLOCKED on the `WorkerInterface` contract-shape ruling** (FLAG-ALIGN-1 (c)): `WorkerInterface` is a Phase-0-frozen contract, and ADR-054 §8 retains class *names* but does **not** amend the contract *surface* — whether the aligned contract removes `run()`/`shutdown()`, retains them as no-ops, or adds a new bounded-cycle method is an architect ruling, not a mid-implementation design choice. Do not change the contract until FLAG-ALIGN-1 is ruled. *Authority: Doc 8 v2.0 §9/§23/§25; ADR-054 §1/§8; WorkerInterface = P0-frozen contract.*
- **T2 — Wire the Processing Engine cycle binding + config read.** Add a container binding for the cycle that reads `processing.*` (batch sizes + `cycle_time_budget_seconds`) from `config/worker.php`, composing the four stages. Retire `worker.engine.event`/`worker.engine.maintenance`/`dispatcher.engine` daemon bindings from the execution path (keep the strategy bindings). *Authority: Doc 8 v2.0 §9; ADR-054 §1; ADR-012.*

### B. WP-Cron trigger registration (activation scheduling, deactivation cleanup, execution entry point)

- **T2a — Register a processing-cycle WP-Cron event + callback.** Follow the `ReconciliationCronRegistrar` precedent exactly (custom-interval registration + `wp_next_scheduled` guard + config-driven cadence): register a recurring cron hook whose callback runs **one bounded Processing Engine cycle** on the worker-bootstrapped process. Bind the callback in `headless-sync.php` mirroring the L58-66 reconciliation block. The reliable-cadence operator path is a system cron invoking `wp cron event run --due-now` (a *trigger*, not a daemon). *Authority: Doc 8 v2.0 §23; ADR-054 §1/§23.*
- **T2b — Activation scheduling / deactivation cleanup.** `Application::activate()` schedules the processing-cycle event (and reconciliation events, for consistency) so synchronization begins on activation with zero configuration (Principle 8); `Application::deactivate()` clears them via `wp_clear_scheduled_hook`. *Authority: Doc 8 v2.0 §2b/§24; ADR-054 §1/§8b.*
- **T2c — No `hsp worker` daemon command.** Explicitly do NOT add a long-running `hsp worker`/`hsp process` CLI daemon (that is the superseded ADR-024 surface). The cadence trigger is `wp cron event run` against the registered event. *Authority: ADR-054 §1 (supersedes ADR-024); Doc 8 v2.0 §23.*

### C. Processing Health / heartbeat

- **T3 — Make maintenance cadence stateless-cycle-safe.** `MaintenanceWorkerStrategy`'s in-memory `$lastSweepAt` cadence gate does not survive a per-cycle process exit (every cycle would sweep). Replace with a **durable/derived** cadence (e.g. a config-scheduled maintenance cron cadence, or a cadence derived from queue state) so requeue sweeps run at the intended interval across independent cron cycles — **without new persistence or schema** (DECISION Q/ADR-054 §9). *Authority: Doc 8 v2.0 §2/§9; DECISION R.*
- **T3a — Per-cycle heartbeat semantics.** Record a current-state heartbeat per cycle (bootstrap + end) into the unchanged `system.worker_heartbeats` schema, with `status` from the Doc 8 §16 set (`'running'`/`'idle'`) and `worker_id` per the FLAG-ALIGN-1 ruling. The `DatabaseHeartbeatPublisher` SQL and DECISION P schema are **reused verbatim**. **BLOCKED on FLAG-ALIGN-1** for the identity + status-value ruling. *Authority: Doc 8 v2.0 §15/§16; ADR-054 §5/§8.*

### D. Operations console / providers / metrics

- **T4 — Add cycle metrics; reinterpret health/worker signals. BLOCKED on FLAG-ALIGN-1.** Extend `MetricsProvider` (derived-on-demand, DECISION Q — zero new persistence) with **cycles_completed / avg_cycle_duration / per_stage_throughput**. **Feasibility is contingent on FLAG-ALIGN-1's identity ruling:** deriving cycles_completed / avg_cycle_duration on-demand with zero persistence works ONLY if heartbeat row cardinality supports it — fresh-UUID-per-cycle yields countable recent-cycle rows queryable on demand; stable-per-stage identity does NOT (one current-state row per stage), and would force either new persistence (**prohibited** by ADR-054 §9 / DECISION Q) or log-derived metrics (structured logs are **not** a DECISION Q on-demand query surface). So FLAG-ALIGN-1 decides T4's **feasibility**, not only its semantics. The health/worker *reinterpretation* half (reframe `HealthProvider::workersReport()` as "processing stalled: heartbeat stale WHILE queue non-empty"; reinterpret `WorkerStatusProvider`/`WorkerStatus.online`/`DashboardView` + `OperationsQueryReader` docblock as **cycle-freshness**) is not cardinality-dependent — age-query and heartbeat-read mechanisms are **preserved** (DECISION P reused verbatim) — but is grouped under T4 and proceeds once the identity ruling lands. *Authority: Doc 8 v2.0 §15-17/§27; ADR-054 §5/§6/§9; DECISION Q.*
- **T4a — Reconcile DECISION V (f) daemon language in the console.** `WorkerStatusProvider`/`WorkerStatus` docblocks assert "worker lifecycle belongs to the process supervisor." Under ADR-054 there is no supervisor; the surface stays read-only, but the *reason* changes ("cron may not be firing" → runbook, not "the supervisor owns restart"). This is a **DECISION V (f)** wording conflict — cross-reference the Conflict Report; the read-only-console guarantee itself is unchanged. *Authority: ADR-054 §5; DECISION V (f).*

### E. CLI surface

- **T5 — Config keys for the Processing Engine (FLAG-DOC8V2-2).** Add `processing.relay_batch_size` / `processing.dispatch_batch_size` / `processing.projection_batch_size` / `processing.cycle_time_budget_seconds` to `config/worker.php` with sensible defaults, and wire the engine to read them — following the **DECISION R config-driven-cadence precedent** (no hardcoded values). **This is the FLAG-DOC8V2-2 owed work; a FUTURE implementation session adds it. It is NOT added by ALIGN-S0.** *Authority: Doc 8 v2.0 §9; FLAG-DOC8V2-2; DECISION R (precedent).*
- **T5a — CLI surface: no change owed.** `hsp dlq|replay|reconcile|status` are all trigger-agnostic operator surfaces preserved by ADR-054. No CLI worker-launch command is owed. *Authority: ADR-054 §7/§9.*

### F. Onboarding prerequisite

- **T6 — Resolve the DECISION W (c) backfill worker-heartbeat prerequisite under cycle-freshness.** `BackfillGate::workerGate()` currently requires a "live worker heartbeat" and its remediation says "start/restart the worker via your supervisor." Under ADR-054 the prerequisite must mean "a processing cycle is running/scheduled (cron is firing)," and remediation must be "ensure WP-Cron / `wp cron event run` is firing," not "restart the daemon." ## 6. New flags raised by this audit (needed-ruling — NOT resolved here)

### FLAG-ALIGN-1 — Per-cycle processing-component identity (UUIDv7) + heartbeat status value set under the cycle model

**Raised:** 2026-07-17 | **Session:** ALIGN-S0 | **Status:** OPEN — needs an architect ruling before T1/T1a/T3a/T4 code is written; NON-BLOCKING for this audit. Gates the `WorkerInterface` contract shape (T1a) and T4 metrics feasibility.

Doc 8 v2.0 §8/§15/§24 and ADR-054 §8 say `worker_id` is a **per-cycle** UUIDv7 processing-component identity "self-assigned at cycle bootstrap," and §16 defines the status set as `'running'`/`'idle'` (removing `starting/recycling/stopping/failed`; ADR-054 removes `'shutdown'`). The implementation assigns `worker_id` **once at construction** and "never changes during the worker lifetime" (`WorkerEngine.php` L159; `WorkerInterface.php` L11; `RelayWorkerStrategy.php` L55), and `HeartbeatRecord`/`WorkerEngine::tick()` emit `'processing'`/`'idle'`/`'shutdown'`. **The ruling needed:**

- **(a)** does each cron cycle mint a **fresh** UUIDv7 (so `system.worker_heartbeats` accumulates one row per recent cycle — which is what makes `worker_count` = "cycles/stages that ran recently" per §6), or is identity **per-stage-per-cron-schedule** (a stable id per stage so the current-state table stays small)? The two give different `worker_count`/health semantics.
- **(b)** confirm the status value set is exactly `'running'`/`'idle'`.
- **(c) `WorkerInterface` contract shape.** `WorkerInterface` is a **Phase-0-frozen contract**; ADR-054 §8 retains class *names* but does **not** amend the contract *surface*. Does the aligned contract **remove** `run()`/`shutdown()`, **retain** them as no-ops, or **add** a new bounded-cycle method? This gates T1a and must be ruled here — it is not a mid-implementation design decision. (Do not choose an option.)

**Cardinality/feasibility consequence (rule with this in view — it decides T4's FEASIBILITY, not only its semantics):** the identity choice in (a) determines whether ADR-054 §17/§27 **cycles_completed / avg_cycle_duration** can be **derived on-demand with zero persistence** (DECISION Q). **Fresh-UUID-per-cycle** yields countable recent-cycle rows an on-demand aggregate query can count/average → T4 is feasible as a Minor addition. **Stable-per-stage identity** gives one current-state row per stage (no per-cycle history) → cycles_completed/avg_cycle_duration cannot be derived on-demand, and would require either **new persistence** (prohibited by ADR-054 §9 / DECISION Q) or **log-derived** metrics (structured logs are not a DECISION Q on-demand query surface). So this ruling makes T4 either feasible-as-specified or blocked-pending-a-different-metric-strategy.

**Do not improvise** — this changes the heartbeat row cardinality and every derived worker/health/metric signal, the `WorkerInterface` contract surface (c), and T4's feasibility. Recorded per the audit rule (STOP classifying and flag when a ruling is absent).

### FLAG-ALIGN-2 — DECISION W (c) backfill "live worker heartbeat" prerequisite under cycle-freshness heartbeats

**Raised:** 2026-07-17 | **Session:** ALIGN-S0 | **Status:** OPEN — needs an architect ruling before `BackfillGate::workerGate()` is realigned; NON-BLOCKING for this audit.

DECISION W (c) requires "a live worker heartbeat is a HARD PREREQUISITE" for backfill and says workers "drain as normal (they are the execution path)"; `BackfillGate::workerGate()` remediation currently instructs the operator to "Start (or restart) the HSP worker via your process supervisor (systemd / Supervisor / container) … the supervisor owns worker lifecycle" (`BackfillGate.php` L101-105). Under ADR-054 §5 there is **no supervised worker** — a fresh `system.worker_heartbeats` row now means "a processing **cycle** ran recently," and a missing/stale one means "**cron may not be firing**," not "a daemon is down." **The ruling needed:** what exactly satisfies the DECISION W (c) prerequisite under the cycle model — (a) a fresh cycle heartbeat within the offline threshold (the existing age read), (b) proof the processing-cycle **cron event is scheduled + WP-Cron is enabled**, or (c) both? — and what the remediation should say ("ensure WP-Cron is firing / run `wp cron event run`", not "restart the daemon"). The `BackfillService` no-in-request-drain design and the re-emission repair path are unaffected and preserved either way; only the gate's **meaning + remediation** need the ruling. Recorded per the audit rule; not improvised.
